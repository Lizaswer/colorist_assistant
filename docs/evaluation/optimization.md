# Optimization experiment: Colorist Assistant

## 1. Что было

Проект **Colorist Assistant** помогает колористу. Калькулятор формулы работает по правилам колористики, а отдельный ИИ-ассистент помогает мастеру и обращается к внешнему OpenAI API.

Для эксперимента оптимизировался запрос ИИ-ассистента.

Pipeline:

`input → preprocessing → model/API → postprocessing → result`

## 2. Измерение ДО оптимизации

Один и тот же вопрос мастера был повторён 3 раза.

Среднее время:

| Этап | Среднее |
|---|---:|
| input | 0.0000 s |
| preprocessing | 0.0000 s |
| **model/API** | **8.4392 s** |
| postprocessing | 0.0000 s |
| result | 0.0000 s |
| **pipeline** | **8.4392 s** |

### Найденный bottleneck

**Внешний model/API — 8.4392 s.**

Именно внешний LLM-вызов является реальным медленным участком измеренного pipeline.

## 3. Что поручили AI

После измерения AI было поручено:

> Найти варианты оптимизации именно для найденного bottleneck и выбрать один вариант для реализации.

Оптимизация выбиралась **после измерения**, а не до него.

## 4. Что предложил AI

Для внешнего LLM-вызова были рассмотрены следующие направления:

- caching повторяющихся запросов;
- уменьшение количества LLM-вызовов;
- уменьшение передаваемого контекста;
- использование более быстрой модели.

Для эксперимента выбран **caching**, потому что тестовый сценарий специально содержит повтор одного и того же вопроса.

## 5. Одно реализованное изменение

Добавлено кэширование ответа ИИ-ассистента для одинакового запроса и одинакового контекста.

Логика:

```text
Новый запрос
    ↓
cache miss
    ↓
OpenAI API
    ↓
ответ
    ↓
сохранить в cache

Повторный запрос
    ↓
cache hit
    ↓
ответ из cache
```

Rule-based калькулятор при этом не изменялся.

## 6. Измерение ПОСЛЕ оптимизации

Тот же сценарий дал:

```text
round 1 → API call  → 6.7919 s
round 2 → CACHE HIT → 0.0001 s
round 3 → CACHE HIT → 0.0001 s
```

Среднее время pipeline:

**2.2640 s**

## 7. Итог

Главная цепочка результата:

**8.4392 s → bottleneck: model/API → caching → 2.2640 s**

Эффект для выбранного повторяющегося сценария:

- среднее время уменьшилось примерно на **73.2%**;
- ускорение составило примерно **3.7×**;
- вместо трёх LLM-вызовов выполняется один, два следующих запроса обслуживаются из cache.

## 8. Где AI оказался недостаточно хорош

Первая локальная версия эксперимента до подключения реального внешнего API привела к гипотезе про локальную JSON-сериализацию.

После подключения настоящего OpenAI API и повторного измерения стало видно, что главным bottleneck является не сериализация, а внешний `model/API`.

Это важный результат: **AI может предложить гипотезу, но bottleneck определяется измерением реальной системы.**

## 9. Ограничение оптимизации

Caching не ускоряет новый уникальный вопрос.

Первый уникальный запрос всё ещё проходит через OpenAI API. Оптимизация предназначена для повторяющихся запросов, retry и ситуаций, когда мастер задаёт один и тот же вопрос повторно.

Поэтому `2.2640 s` — это среднее именно для сценария:

`1 API call + 2 cache hits`.

## 10. Как проверили

Проверка состояла из:

1. benchmark ДО оптимизации;
2. реализации одного изменения — caching;
3. benchmark ПОСЛЕ оптимизации;
4. проверки, что повторный запрос даёт `CACHE HIT`, а не новый LLM-вызов;
5. проверки проекта тестами.

## 11. Финальная формулировка для защиты

> **До:** 8.4392 s  
> **Bottleneck:** внешний model/API  
> **Гипотеза AI:** caching повторяющихся запросов  
> **Изменение:** кэширование ответов AI-ассистента  
> **После:** 2.2640 s  
> **Результат:** среднее время повторяющегося сценария уменьшилось примерно на 73.2%, а число LLM-вызовов — с трёх до одного.
