# Spec-Driven Development (SDD)

## Суть

Сначала пишется спецификация — **что** строим и **зачем**, — и только потом решается **как**.
Спецификация становится главным артефактом: по ней ИИ-агент и люди планируют,
пишут код и проверяют результат. Код вторичен и может быть переписан,
если спецификация не изменилась.

В формулировке [GitHub Spec Kit](https://github.com/github/spec-kit/blob/main/spec-driven.md)
это «инверсия власти»: не спецификация служит коду, а код служит спецификации.
Поддерживать продукт значит развивать спецификацию; код — её выражение
в конкретном языке. Такой цикл стал практичным, когда ИИ может реализовать
достаточно точный текст требований, но без структуры генерация расползается.

## Этапы в GitHub Spec Kit

Самый известный инструмент — [GitHub Spec Kit](https://github.com/github/spec-kit).
Его цикл:

1. **Constitution** — принципы проекта, задаются один раз.
2. **Specify** — требования и цели: что и зачем, без технологий.
3. **Plan** — технический подход: стек, архитектура.
4. **Tasks** — разбиение на задачи.
5. **Implement** — реализация по спецификации.
6. **Converge** — проверка, что результат соответствует спецификации.

Подробнее — [описание подхода](https://github.com/github/spec-kit/blob/main/spec-driven.md)
в репозитории Spec Kit и [разбор от Microsoft](https://developer.microsoft.com/blog/spec-driven-development-spec-kit/).

## Как это ложится на наш проект

| Этап SDD | У нас |
| --- | --- |
| Constitution | Принципы в [02-concept.md](02-concept.md): правила считают, LLM объясняет; каждое решение объяснимо |
| Specify | [02-concept.md](02-concept.md): путь пользователя, рамки, граничные случаи |
| Plan | [03-implementation.md](03-implementation.md) и [05-decisions.md](05-decisions.md) |
| Tasks | План работ в концепции, задачи в README |
| Converge | Эталонные случаи в `data/cases` + `scripts/evaluate.py`: спецификация, превращённая в проверку |

Сильная сторона проекта для SDD: эталонные случаи — это спецификация в исполняемом виде.
Каждое правило колориста можно записать как случай «вход → ожидаемая формула»
до того, как оно реализовано в коде.

Что уже похоже на SDD без установки Spec Kit:

- концепция (`02-concept.md`) не смешивается с реализацией (`03-implementation.md`);
- граничные случаи заданы до кода (отказ на осветление, хна, корни≠длина);
- `data/cases/*.json` — исполняемые сценарии: вход, ожидаемая формула, известный пробел;
- `scripts/evaluate.py` и pytest — шаг Converge: расхождение с эталоном видно сразу.

Что ещё не SDD по-настоящему:

- правила в `knowledge.py` появились из «общих знаний» модели, а не из спецификации колориста;
- нет constitution-файла инструмента Spec Kit и нет команд `/speckit.specify` → `/plan` → `/tasks`.

Решение Р9: на пару Spec Kit не ставим. Если после интервью пойдёт правило «отдельная формула для длины»,
можно провести одну фичу по циклу Specify → Plan → Tasks → Implement и сравнить с тем, как писали ядро.
